The rule

If a section can be described with a sentence that also describes the reference, it is not finished. The reference is a portfolio that argues its work is good. Meridian is a portfolio that measures it and publishes the readings, including the unflattering ones. That distinction has to survive into every plate.

03

Reference teardown

Findings from operating the live build — dispatching missions, running the shell, toggling stock, watching the network. Some of this could not be seen from screenshots, and one finding changes the plan.

The console does not do what its copy says

The section header reads: "Tool calls are real; github.repo queries the public API live." Two missions were dispatched — M-01 and M-03 — and the network log shows zero requests to api.github.com, or anywhere except his own domain for fonts, chunks and the ridge artwork. Every tool result returns in [0ms] or [2ms], which is not a network round trip. The runtime is a local simulation with scripted latency.

The footer is honest about the model — "no model was called to render this page" — but the console copy overclaims the tools. That gap is the reference's one real vulnerability, and anyone technical who opens a network tab finds it in about thirty seconds.

Honesty rules for Meridian

Which makes this a constraint rather than a gloat. The whole premise of this build is a page whose claims are checkable, so it cannot afford a single sentence it would fail on:

  • Never describe a capability the page does not have. If the API is not called, the copy does not say it was.
  • Show real latencies. Meridian's calls take hundreds of milliseconds to seconds. That slowness is the proof — never mask it with cosmetic timings.
  • Label cached results as cached. When a survey is served from the per-SHA cache rather than a fresh API call, the panel says so on the line it affects.
  • Print the receipt. Every number on the page traces to something a visitor can fetch independently.

Worth learning from

The dual-register trace. The estimate-beside-actual footer. Per-theme artwork. Lazy section rendering. Naming the themes after something in the subject's own world rather than "light" and "dark". A shell that indexes the same content the rest of the page shows.

Rejected outright

Claiming live API calls that never happen. Gating real content behind a game. Hand-assigned ranks presented as though measured. Zero-millisecond tool results. An XP economy that rewards clicking rather than reading.

What this sharpens

Before operating it, the difference between the two builds was a claim about ambition. After, it is a claim about fact: his console simulates the thing, Meridian performs it — and Meridian can prove it with a network tab. That is a far stronger position than "mine looks different", and it belongs stated plainly on the page rather than implied.

04

Concept

One recommendation, two live alternates. All three cover the same sections and carry the same engine — only the world changes.

Recommended

Meridian — the observatory

An observatory does not argue about what it sees. It points instruments at things, records magnitudes, publishes a catalogue, and revises that catalogue when the readings change. Objects get reclassified. The log of reclassifications is itself the evidence that anyone is still looking.

That is exactly the machine you described: instruments that read your repositories, measure them on fixed axes, publish an entry, and upgrade it when you improve the work. The metaphor is not decoration here — reclassification-on-new-evidence is literally how astronomical catalogues work, so every feature you asked for has a native name inside it. Rarity becomes class. The auto-promotion becomes a revision. The nightly Action becomes an observing run.

It also gives maximalism somewhere honest to go. Star atlases and survey plates are among the densest documents ever printed and none of that density is ornament — it is coordinates, magnitudes, marginalia, registration marks. That is the licence to be visually loud while staying professional.

Alternate A

The Assay Office

Metallurgical testing: samples come in, get assayed against fixed standards, and receive a hallmark. Classes become purity marks. Strong fit for the "measured, not claimed" thesis and gives a gorgeous stamped-metal visual language. Weaker on the continuous re-measurement idea — an assay happens once, which fights your auto-promotion feature.

Alternate B

The Exchange

Repositories as listed instruments with live ratings, a ticker of upgrades and downgrades, analyst notes. Maps perfectly onto rank changes and suits dense readouts. Risk: finance framing reads as cold, invites "why is your art priced", and the ticker aesthetic is closer to the reference's console than the other two.

What makes this genuinely new

Both research sweeps came back empty on this: star-count leaderboards exist, repo health scoring exists, gamified portfolios exist — but nothing joins them. No project computes rarity tiers from repository evidence and republishes a portfolio without being asked. You are not building a better version of your friend's site. You are building the thing his site is pretending to be.

06

Visual system

Professional, maximalist, lightly pixelated — in that order of priority. Density comes from real data; the pixel face is an accent, not the identity.

Ground and palette

Two surfaces in tension: a deep ink-navy sky and inset chart-paper plates. That dual-ground is the single biggest visual separation from the reference's flat near-black field, and it gives layered composition something to layer against. Neutrals carry a slight blue bias so they read as chosen rather than defaulted.

The accent is a signal amber, used only for live state — something is running, something changed, something needs reading. The six class colours are semantic and separate from the accent: they encode rank and appear nowhere else, which means colour on this page always means something.

Big Shoulders Display — display. Industrial condensed grotesk, 800, uppercase. Chart-label energy, nothing like the reference's pixel headlines.

JetBrains Mono — data. Tabular figures, every number and trace line on the page.
Handjet — pixel. Class chips, plate markers and eyebrows only, roughly five percent of type on screen. Zero overlap with the reference's four — Pixelify Sans, Silkscreen, Instrument Serif, IBM Plex Mono — checked against the live build. All four here are on Google Fonts. This document is set in the stack it prescribes.

Texture and layout

Coordinate grid as a foreground element rather than a background wash. Dithered gradients instead of smooth ones. Plate registration marks, margin rails carrying footnotes, and multi-column survey tables. Composition is asymmetric — plates of different widths butted against each other, marginalia in the gutters. Loud through information, quiet through ornament.

Two ideas taken from the reference

Its XP bar is drawn as pixel segments rather than a solid fill, and its card foil is a single repeating gradient doing the work of an image. Layers 11 and 10 are the same moves — kept because they are genuinely good, and re-valued so neither looks like a copy.

Budget

Two rasters total, both theme-scoped and lazily loaded below the fold. Everything else is CSS. Layers 06 and 12 are the only ones that can cost frames — grain is a static tile, and the live rule animates transform only. If a layer cannot justify itself on a plate showing real measurements, it does not ship.

Motion

Every animation reports something real — a value arriving, a state changing, a rank moving. Timings and easings are fixed below. Everything behind prefers-reduced-motion.

Contrast

Gated in CI. Maximalist density fails fastest on contrast, so it is a build step, not a review note.

Themes

Named for exposure — day plate and night plate. Both grounds designed rather than inverted, separate sky artwork per theme, and class colours revalued so the ramp stays legible on either.

Impact — the first five seconds

Attraction does not come from uniform heaviness; it comes from a few moments strong enough to be remembered and described to someone else. Uniformly heavy pages read as noisy and get closed. What follows is the arrival sequence and the five signature moments, specified rather than left to taste.

The arrival — Plate Development

The single strongest moment on the site, and it is thematically exact: an astronomical survey plate develops. The page opens on bare sky. Over 1400ms the graticule draws in from the top-left origin, the survey plate fades up beneath it through a dither mask so it resolves in visible steps rather than smoothly, and the headline sets. Then the live readout counts from zero to the real figures — objects catalogued, last observing run, most recent class change — and stops on values a visitor can verify in the repository.

It is striking, it is cheap (one raster, one mask, one counter), and it is honest — the motion is the page reporting its own data arriving. Under prefers-reduced-motion the plate is simply present and the numbers are simply correct.

Where the weight goes

Heavy at the top and at the cards, quiet in the reading passages. First Light and the Catalogue carry the density — full graticule, plate artwork, class fields, live readouts. The prose sections drop to plate-on-sky with a margin rail and nothing else, so the arguments stay readable. Loud, quiet, loud is a rhythm; loud throughout is noise.

The line that gets repeated

Every memorable site has one sentence a visitor repeats to someone else. Here it is the thesis, printed in the Colophon and true: no model was called to render this page, and no rank on it was typed by hand. The reference can claim only the first half. That claim is the reason to look, and the design exists to deliver you to it.

The trap to avoid

Every source on the current maximalist revival gives the same warning, and it applies directly here: overcrowded layouts overwhelm, heavy graphics slow load, and contrast is usually the first casualty. The discipline is that density must be earned by content. A plate is allowed to be dense because it is showing eleven real measurements — never because empty space felt underused.

The classification engine

The heart of the build. Deterministic maths decides the class; templates only describe it. This is what stops ranks flickering and what lets any claim be defended.

Five axes

AxisQuestion it answersComputed fromWeight
StabilityDoes it hold together?Test files and ratio, CI workflow present, last CI conclusion, coverage report, lint config, strict typing, licence, unpinned or vulnerable deps0.28
MassHow much is actually there?Commit count (log-scaled), lines of code, package or module count, repo lifespan, distinct languages0.24
AnomalyHow unusual is it?Topic rarity against a corpus, uncommon dependencies, domain distinctness within your own catalogue, bounded rule-based heuristics (±10 max)0.20
LuminosityCan anyone else see it?Deploy URL returning 200, README length and imagery, releases, docs directory, topics set, stars and forks (capped, low weight)0.16
CadenceIs it alive?Recency of last commit, distribution of commits over time, sustained work versus a single weekend, issue and PR activity0.12

Weighting is deliberate: stability outranks size, so a small well-tested library beats a large untested one. And stars sit inside the lightest axis with a cap — popularity contributes, but it can never carry a project on its own.

Score to class

composite = 0.28·stability + 0.24·mass + 0.20·anomaly + 0.16·luminosity + 0.12·cadence

class  MYTHIC     composite ≥ 88
       LEGENDARY  76 – 87
       EPIC       64 – 75
       RARE       50 – 63
       UNCOMMON   34 – 49
       COMMON     < 34

hysteresis   promote  : exceed threshold by +2, hold 2 consecutive runs
              demote   : fall below by −3, hold 3 consecutive runs
              floor    : a class is never revoked within 30 days of being granted

The hysteresis gate is the difference between a feature and an annoyance. Without it, a repo sitting on 75.6 flips between epic and legendary every night and the promotion log fills with noise. With it, a promotion means something actually improved and stayed improved.

Why nothing subjective picks the number

Ask a language model to rank the same repository twice and you get two answers. Ranks would drift with no cause, and the first person to ask "why is this legendary?" gets nothing back. So the pipeline computes the score from evidence, and the model's job is narrower and safer: read the code and the README, then write the prose that explains what the numbers already decided. Every entry can print its own maths on demand via why <repo>.

Calibration — required before launch

Thresholds above are a starting point, not a truth. They must be tuned against your actual repositories, because a rubric calibrated on large mature projects will grade a portfolio of hackathon builds as ten commons, and one calibrated too kindly makes everything legendary and the ladder stops meaning anything. Target distribution for a healthy catalogue: roughly one mythic at most, two or three legendary, and a real tail. The ladder has to be able to say no.

08

Attribution

Your brief asked that contributions be referenced everywhere. Here is how that becomes a feature rather than a liability.

You wrote that the whole repository is essentially your work. The safe and stronger version of that is to show it rather than assert it: the pipeline can compute your authorship share directly — commits by you against total, files touched, lines changed, PRs merged, review comments left — and print it on the entry. A recruiter will check the commit graph regardless, so a number that matches what they find reads as confidence, whereas a claim that overshoots costs the whole page its credibility.

Solo repositories

Entry shows the full build with no authorship footnote needed. These carry the strongest claims and should be the loudest plates in the catalogue.

Shared repositories

Entry carries an authorship strip: 142 / 168 COMMITS OWNER. Precise, verifiable, and more impressive than a vague claim.

The contributions strand. Beyond your own repos, the pipeline searches the API for merged PRs, filed issues and reviews you authored anywhere on GitHub, and surfaces them as their own catalogue class — upstream work against other people's projects, each linked to the exact commit. Your friend's page mentions two upstream findings at Google as a headline number. Yours generates that list automatically and keeps it current, which is both the honest version and the more impressive one.

09

The instrument runtime

No language model, anywhere in this build. The instruments are deterministic programs that make real network calls to the GitHub API and stream real results. The reference fakes agency with a scripted runtime; Meridian drops the pretence and ships the honest version — measurement, not conversation.

InstrumentDisciplineTools

Five, not six — and every one corresponds to a step the pipeline genuinely performs, rather than to a subject area. Four of the five were always deterministic; only Herald ever needed a model, and the section below replaces it. Plumb still matters most: no entry reaches the catalogue until each factual claim is matched to a file that actually exists in the repository. An entry that says "tested against a real Postgres" must point at the compose file that starts one — and that check is a file-tree lookup, not a judgement call.

What replaces the model

Herald composes prose from hard-coded sentence templates filled by real signals — no generation, no API. A repository with tests/, a green CI workflow and a coverage report produces: "47 tests, CI green across the last 12 runs, coverage reported at 88%." True by construction, because every clause is bound to a measured value and a template only fires when its evidence is present.

What templates cannot write is the thesis — the one line saying why a project is interesting. So you write that, once, per project, in prose.json. The machine supplies every number and every claim about structure; you supply the argument. That split is honest and it is also better: the sentences worth reading on the reference site are the ones a person wrote.

Architecture

A Next.js route handler runs the instrument graph and streams over SSE. Concurrency is real — independent probes fire together and settle out of order because they are genuine network calls to the GitHub API, not timers. No key to protect, no server-side secret beyond a read-only GitHub token.

Controls

The only budget is the GitHub rate limit: 5,000 requests an hour authenticated. Responses are cached to disk per commit SHA, so repeat runs cost nothing. Rate-limit exhaustion serves the cached survey and says so on the panel.

Trace grammar

Adapted from the reference's best idea — a machine line and a human line, so the panel is legible to a recruiter and verifiable by an engineer. The difference is that every value below is real, including the latency. The reference's tool calls return in 0ms because nothing leaves the browser; these return in hundreds of milliseconds because a request genuinely goes to api.github.com and comes back.

header  4 STEPS · 3 STAGES · 11 API CALLS  est.

Estimate in the header, truth in the footer — but the meter counts API calls and cache hits instead of tokens and dollars. A visitor who opens a network tab finds exactly what the panel described. That correspondence is the entire credibility of the page, and without a model in the loop it is now trivially true rather than something you have to engineer.

What this costs you, and what it buys

Costs: the instruments cannot read a repository and understand it. They can see that tests/ exists and count the files in it; they cannot tell you the tests are any good. Every judgement of quality in the catalogue is either a measured proxy or a sentence you wrote yourself.

Buys: zero running cost, no key to leak, no rate-limited public endpoint that a stranger can drain, nothing that can hallucinate a claim about your work, and a page that is fully reproducible — anyone can clone the repo, run the engine and get byte-identical scores. The reference's footer boasts "no model was called to render this page" as a footnote while the console overclaims. Yours can print the same sentence as a thesis, and have it be completely true.

Automation

Requirements R8, R9 and R10 — the button, the automatic card, and the automatic promotion. One pipeline covers all three.

trigger   workflow_dispatch  ← your button, and the only trigger
           inputs: repo (optional — blank surveys everything)
                   dry_run (report the diff, commit nothing)
           NO cron. NO push trigger. It runs when you say so.

01 collect   list repos (REST + GraphQL) · fetch tree, workflows, CI runs,
              releases, languages, commit history, your authorship share
              search merged PRs + issues you authored across all of GitHub

02 measure   compute five axes from evidence · no model involved
              write scores.json with every raw signal preserved

03 diff      compare against catalogue.json
              new repo?        → mark FOR DRAFTING
              class changed?   → test hysteresis gates
              nothing moved?   → exit, no commit

04 compose   Prism extracts signals → Herald fills hard-coded templates
              → Plumb verifies every claim against real files
              a template whose evidence is missing simply does not fire
              no thesis line yet?  → entry publishes as UNANNOTATED

05 revise    class change passes gates → update entry
              → append to revisions.json with the cause:
                "COMPLYLITE · EPIC → LEGENDARY · stability 61 → 88
                 (CI added, 47 tests, coverage report)"

06 publish   commit catalogue.json + revisions.json → deploy

Manual trigger only

No schedule. The workflow appears in the Actions tab with a Run workflow button, and nothing happens until you press it. That keeps R8 exactly as you wrote it — click the button, the instruments survey the repositories, the ranking comes back — and it means the repository history stays clean instead of accumulating a commit every night reporting that nothing changed.

R9 and R10 still hold: you never ask for a card or a promotion. You press one button and the pipeline decides what is new, what moved, and what to write. dry_run lets you see the diff before anything is committed.

The feature to push hardest

The revisions log. When your epic becomes legendary, do not just swap a badge — publish why, dated, with the axis that moved and the evidence that moved it. A portfolio that visibly levels up as you work, with receipts, is something nobody else currently has. Put it on the hero.

contributions.json — upstream PRs and issues
rubric.json — weights and thresholds, version-stamped

Version-stamping the rubric matters more than it looks: when you tune thresholds later, every historical revision stays interpretable because it records which rubric version produced it. Without that, a rubric change silently rewrites your own history.

12

Build order

Engine before interface, deliberately. If the scoring is wrong, a beautiful catalogue is a beautiful catalogue of wrong answers.

00Calibrate

Read your real repositories

Pull the account, compute raw signals, look at the distribution, tune thresholds until the ladder discriminates. Nothing else can start until this is honest.

01Engine

Scoring as a library, no UI

Five axes, deterministic, fully unit-tested. Runs as a CLI and prints a table. Reviewable and arguable before a single pixel exists.

02Pipeline

Actions, drafting, revisions

Manual dispatch trigger with inputs, diff logic, Herald's template set and Plumb, the revisions log. At the end of this phase the automation is real even though the site is not.

03System

Design system and static plates

Tokens, both themes, type scale, class ramp, contrast gate in CI. Then First Light, Parallax, the Log, Hailing.

04Catalogue

The catalogue and constellation

Entries rendered from catalogue.json, class filters, score breakdowns, the radial skill view, the revisions feed.

05Runtime

The observing run

Deterministic instruments, streamed over SSE with a call meter and disk cache. Last because it is the least load-bearing and the easiest to get wrong and depends on everything above.

06Harden

Ephemeris, a11y, performance

Command line, reduced-motion paths, Lighthouse and axe budgets enforced, mobile density review, cost ceiling verified.

Done means

  • Pushing an improvement to a repo, then pressing Run workflow once, results in a re-classified entry and a revisions line — with no other manual step and nothing written by hand.
  • Creating a brand-new repo produces a drafted catalogue entry without anyone asking for one.
  • why <repo> prints the five axis scores, the raw signals behind each, and the threshold arithmetic.
  • Every factual sentence in every entry points at a file that exists in that repository.
  • Class distribution is a real curve — not everything is legendary.
  • The console makes genuine parallel tool calls, and the page never claims otherwise.
  • A visitor with a network tab open sees requests matching every claim the console makes.
  • Displayed latencies are measured, never authored.
  • No section of the page is hidden until a visitor interacts with something.
  • Authorship share is computed and shown on every shared repository.
  • Contrast passes at every class colour on both grounds, enforced in CI.
  • Reduced-motion and keyboard paths are complete.
  • No section can be described by a sentence that also describes the reference.

AGENTS. Five instruments — Sextant (measure), Prism (read code),

network is genuinely concurrent. Prose comes from hard-coded templates
bound to measured signals; a template fires only when its evidence is
present. Thesis lines are hand-written by the author in prose.json.
Budget is the GitHub rate limit; responses cached per commit SHA.
Trace uses a dual register — machine line then plain-language line:

append cause to revisions.json → commit → deploy. The revisions log is a
headline feature: publish why a rank moved, dated, with evidence.
